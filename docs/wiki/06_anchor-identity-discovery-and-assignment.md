# Anchor Identity, Discovery, and Assignment

> **Related pages:** [Connected Routing](05_connected-routing-and-reliable-delivery.md) · [Anchor Self-Setup](07_anchor-self-setup-survey-and-geometry.md) · [Persistence and Recovery](08_data-custody-persistence-and-recovery.md) · [Verified Deployment](11_verified-deployment-and-qualification.md)

This chapter follows the infrastructure behind the participant story: before an anchor can attach a trustworthy location to a click, the system must know which physical anchor spoke and which logical order it currently owns.

---

## Stable Hardware Identity

Every production anchor runs the same `mesh_anchor` artifact. The common image derives a stable node ID from that board's nRF FICR identity, while the gateway assigns and persists the logical discovery and ranging order; a production anchor's slot is therefore runtime state, not a value compiled into a board-specific image ([CMakeLists.txt:212-230](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/CMakeLists.txt#L212-L230), [README.md:75-79](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/README.md#L75-L79)). This distinction matters operationally: replacing a board changes the physical identity, but reordering anchors does not require rebuilding firmware.

At startup, the Zephyr adapter reads both 32-bit FICR device-ID words and hands them to the platform-independent identity mapper ([app_device_identity.c:17-30](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_device_identity.c#L17-L30)). The mapper joins those words into one 64-bit hardware value, XORs it with an anchor-domain constant, and rejects zero or all-ones values before exposing the mapped anchor ID ([device_identity.c:5-29](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/src/device_identity.c#L5-L29)). The application returns zero until initialization succeeds and panics if lazy initialization cannot establish a valid identity, so an anchor does not continue under an invented fallback ID ([app_device_identity.c:39-49](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_device_identity.c#L39-L49)).

Do not transfer the per-slot mental model from the ML collection line to production. The `ml_anchor_1` through `ml_anchor_8` presets deliberately compile deterministic IDs and discovery slots for data collection, but those images are outside the production contract ([AGENTS.md:49-56](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/AGENTS.md#L49-L56), [CMakeLists.txt:161-182](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/CMakeLists.txt#L161-L182)).

## Discovery and Here-I-Am Claims

Anchor setup has two correlated but separate radio lifecycles. A **Here-I-Am** request asks the gateway to publish a current route advertisement over the production Channel 5 flood path, giving anchors fresh gateway-route evidence before enumeration. Its successful terminal proves the bounded gateway flood completed; it does not prove reception by every anchor because Here-I-Am has no per-anchor ACK ([Gateway Here-I-Am Stress Coverage.md:3-37](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/Documentation/Gateway%20Here-I-Am%20Stress%20Coverage.md#L3-L37)).

For an ordinary GUI-triggered assignment, the host freezes the target and runtime profile, performs that separately correlated Here-I-Am preflight, and sends the assignment only after the exact successful preflight terminal. The assignment profile carries the expected anchor count, total operation budget, and equal randomized response spread. Firmware rejects conflicting legacy TLVs or unsafe values, then creates a fresh nonzero epoch and one collection window ([Mesh Connected Routing Contract.md:19-64](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/Documentation/Mesh%20Connected%20Routing%20Contract.md#L19-L64), [app_anchor_gateway_control.inc:607-739](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_anchor_gateway_control.inc#L607-L739)).

Every anchor uses the same response policy regardless of route depth. Its first response delay is `100 ms + random % response_spread_ms`; later retries use bounded exponential backoff. The response deadline then adds route-depth-aware custody time, so deeper anchors get transport time without being given higher priority ([discovery_assignment.h:18-59](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/include/discovery_assignment.h#L18-L59), [discovery_assignment.c:546-630](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/src/discovery_assignment.c#L546-L630)). Each anchor accepts only a well-formed claim for the current epoch, ignores a retired or stale epoch, and retains exact response custody rather than rebuilding a different response for a repeated flood copy ([app_discovery_assignment_policy.h:113-137](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_discovery_assignment_policy.h#L113-L137), [app_anchor_commands.inc:270-493](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_anchor_commands.inc#L270-L493)).

The gateway validates the command, assignment phase, success status, nonzero source, claim hash, and optional hop count before consulting mutable operation state. A live result must still belong to the active epoch and deadline; a fully validated CLAIM or table ACK that arrives after its operation retired is classified as a semantic duplicate so the gateway sends the transport ACK that releases relay custody, but it cannot mutate the current roster or ACK mask. Malformed identities remain unacknowledged, exact live duplicates are idempotent, capacity exhaustion is explicit, and the previous hop remains reverse-path evidence. The expected count is an early-completion hint and a host qualification target; it does not erase useful claims merely because the full expected roster was not heard ([app_anchor_gateway_control.inc:741-1006](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_anchor_gateway_control.inc#L741-L1006), [Mesh Connected Routing Contract.md:522-576](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/Documentation/Mesh%20Connected%20Routing%20Contract.md#L522-L576)).

That correlation boundary is what turns “an anchor was heard” into an assignment claim belonging to this run. The [connected-routing chapter](05_connected-routing-and-reliable-delivery.md) explains how the flood and return path carry these controls.

## Assignment Table Publication

Once claim collection closes, the gateway hashes and deterministically sorts the distinct physical anchor IDs, breaking a hash tie with the full ID, and assigns publication slots `0..N-1` in that order ([discovery_assignment.c:130-225](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/src/discovery_assignment.c#L130-L225)). Each wire entry contains the 64-bit anchor ID, its 64-bit hash, and one-byte slot. The table declares the fixed slot capacity and entry count; parsing rejects malformed ordering, hashes, duplicates, slot gaps in the publication, or inconsistent counts ([discovery_assignment.h:15-28](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/include/discovery_assignment.h#L15-L28), [discovery_assignment.c:300-545](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/src/discovery_assignment.c#L300-L545)).

The command sequence is the table generation within the assignment epoch. Anchors retain the committed epoch, generation, and fingerprint, accept an exact replay so a lost ACK can be regenerated, reject conflicting or older publications, and refuse a table for an epoch they never claimed as a late-claim case ([app_discovery_assignment_policy.h:139-220](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_discovery_assignment_policy.h#L139-L220)). Persisting the table and returning its ACK are separate phases, so the gateway keeps a response-ACK settle window open before finalization rather than racing the last ACK against table completion ([discovery_assignment.h:27-33](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/include/discovery_assignment.h#L27-L33), [discovery_assignment.c:650-682](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/src/discovery_assignment.c#L650-L682)).

Publication success is based on committed ACKs, not merely transmit admission. The gateway records ACKs only for anchors in the current table with the current epoch and generation; a duplicate ACK does not increase completion twice. When the table-delivery attempt and settle window end, it forms the durable membership and final mapping from **ACKed entries only**. A missing ACK excludes that anchor without revoking other committed anchors, so the resulting logical slots may contain gaps. At least one committed anchor is required for firmware success; terminal telemetry reports committed and missing counts separately ([app_anchor_gateway_control.inc:155-279](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_anchor_gateway_control.inc#L155-L279), [app_discovery_assignment_policy.h:302-321](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_discovery_assignment_policy.h#L302-L321)).

The telemetry publisher is statically required to cover 50 anchors. It stages committed mappings, collection completion, schedule readiness, and terminal counters in order, retaining the active event until the host stream takes custody ([app_gateway_assignment_publisher.c:47-175](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_gateway_assignment_publisher.c#L47-L175), [app_gateway_assignment_publisher.c:346-419](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_gateway_assignment_publisher.c#L346-L419)).

## Persistence and Provisioning Evidence

An anchor does not ACK first and hope persistence works later. When its ID appears in the table, it writes a snapshot containing the epoch, table generation, table fingerprint, local and gateway identities, assigned slot, slot count, and provisioned state; only after that save succeeds does it commit the assignment in RAM and schedule the table ACK ([app_anchor_commands.inc:1283-1397](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_anchor_commands.inc#L1283-L1397)). If the anchor is absent, it persists an explicit unprovisioned tombstone instead of retaining an obsolete normal-click slot ([app_anchor_commands.inc:1398-1442](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_anchor_commands.inc#L1398-L1442)).

On reboot, the anchor restores the record only when it is valid and bound to the current local and gateway IDs. Invalid records are cleared, while a missing, disabled, or failed NVS restore leaves the anchor explicitly unprovisioned rather than manufacturing a slot ([app_anchor_init.inc:122-210](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_anchor_init.inc#L122-L210)). At the gateway, finalization persists a membership roster containing only ACKed anchors before it emits success; a membership failure turns the operation into an explicit internal error rather than publishing volatile state ([app_anchor_gateway_control.inc:155-217](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/app/src/app_anchor_gateway_control.inc#L155-L217)). The [persistence and recovery chapter](08_data-custody-persistence-and-recovery.md) follows this pattern across the wider system.

The headless provisioning tool deliberately applies a stricter qualification policy than ordinary firmware success. It correlates events by command kind, correlation ID, host session, and host sequence; requires the requested number of unique claims and published mappings; checks contiguous slots; requires collection-complete and table-publication stages; and rejects terminal counters unless every expected table ACK succeeded with zero failures or lost events ([provision_mesh_anchor.py:188-350](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/scripts/provision_mesh_anchor.py#L188-L350)). Its reachability qualification runs Here-I-Am first and then a separately correlated assignment, preserving the boundary between a successful local announcement flood and proved per-anchor assignment completion ([provision_mesh_anchor.py:680-747](https://github.com/Jubliano-sama/IMEC2/blob/fda75299b34b5ec207fedd387f48e3d2652b5aea/firmware/scripts/provision_mesh_anchor.py#L680-L747)).

For normal operation, the lifecycle proof is the correlated terminal plus the committed roster and explicit missing count. For strict provisioning qualification, the condition is stronger: the requested complete roster was claimed, every listed anchor durably committed its slot, all ACKs completed, and the host saw lossless terminal evidence before moving into [anchor self-setup](07_anchor-self-setup-survey-and-geometry.md).
