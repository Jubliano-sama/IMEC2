# Anchor and clicker power audit

Audit date: 2026-09-05. Source: `474ef8600ef25b50da5c3dbc1dc30241178d166a`. Scope: the production `mesh_clicker` and `mesh_anchor` presets, their board power handling, radio receive/transmit waits, GPIO gesture ownership, battery indication, diagnostics, and current Channel-5 delivery. This was a source audit; no firmware/configuration changes, hardware actions, or current measurements were performed. Line references below are physical file lines, including for `.inc` files that contain compiler `#line` directives.

The clicker already has the right basic sleep architecture. The clearest remaining software work is to fix battery-divider cleanup failure handling, eliminate indefinite held-button polling, and avoid production diagnostic work outside qualification. Further active-radio savings need hardware measurements; shortening wake trains or sleeping through an owned receive window would compromise required behavior.

The 2026-09-03 `Documentation/Channel 5 Delivery Protocol.md`, including its 2026-09-05 implementation notes, supersedes the old Channel-9 connection design. Retained Channel-9 helper names in the code do not mean that production still uses that radio lane. This audit uses the current implementation for timing claims.

## Confirmed defect: periodic battery sampling can leave the divider powered after an error

**P2 — `firmware/app/src/app_board.c:178-207,231-250`; `firmware/app/src/app_battery_indicator.c:100-112`.** `battery_adc_divider_enable()` first configures the enable GPIO low, then separately writes it low. If the second call fails after the first succeeded, `battery_sample_lithium_mv()` returns immediately without calling its cleanup helper. A partial configuration failure is likewise not followed by an attempt to restore the disabled state. After later ADC failures the cleanup helper does run, but when both sampling and disable fail it returns only the primary error. The periodic indicator treats every negative result as an unavailable reading and schedules another attempt, so inability to prove the divider off is not distinguished from an ordinary ADC conversion error.

This occurs after retained idle has already been established. The careful cleanup at `app_clicker.c:4095-4100` therefore does not protect the next periodic reading. A failed disable can leave the divider energized until a later successful cleanup, with no terminal bound if the failure repeats. The clicker idle watchdog checkpoint is taken before the ADC operation, so repeated ordinary retries can continue feeding the watchdog while this power fault persists. The divider current is not known from these source files; no numerical leakage claim is made.

**Smallest corrective direction:** attempt divider-off cleanup on every exit after enable was attempted, retain cleanup failure separately from sample failure, and use bounded cleanup/recovery when the off state cannot be established. Preserve the existing ordinary ADC-error retry and the idle watchdog checkpoint. Add fault-injection cases for enable-configure success followed by set failure, ADC failure plus disable failure, eventual cleanup recovery, and repeated cleanup failure; prove that subsequent clicks and battery samples are still admissible after recoverable errors. No fix was applied during this audit.

## Improvements that can preserve product behavior

### 1. Replace indefinite held-button polling with release-edge ownership

`firmware/app/src/app_config.h:98` sets `CLICK_BUTTON_RELEASE_POLL_MS` to 5 ms. `click_button_release_work_handler()` at `app_clicker.c:4485-4516` reschedules itself every time the input remains pressed, with no elapsed-time cutoff. An ordinary idle clicker is interrupt-driven; a button held by a pocket or jammed mechanism instead requests up to approximately 200 callbacks/s for as long as it stays down. The actual callback rate is lower when execution and scheduler delays are included. This is CPU wakeup overhead, not 100% CPU duty.

Use an armed release edge plus the existing serialized press-cycle owner, with read-after-arm reconciliation so a release between sampling and interrupt setup cannot be lost. Keep short bounded polling for uncertain GPIO state and existing reset recovery. A long-press threshold timer can remain independent. Preserve press timestamps, debounce, long-press/self-test interpretation, pending click FIFO, and exact release/repress ordering. Required tests are press/release at every arm boundary, bounce, held input across a completed action, IRQ setup failure, release while work is pending, and the next full gesture after each recovery. Merely increasing the poll interval changes release latency and is not equivalent.

### 2. Stop diagnostic processing outside an active qualification capture

Ordinary Zephyr logs are already capped at warnings in `firmware/app/conf/mesh-route-test.conf:12-13`; lowering `prj.conf`'s apparent default debug level alone would not address the remaining work. Production CMake enables exact-preset stack diagnostics for clickers and anchors at `firmware/app/CMakeLists.txt:102-113,144-157`. `status_debug_printf()` at `app_board.c:563-600` still formats and attempts RTT output whenever the connected mesh runtime is enabled, even without a reader. The nonblocking writer at `app_board.c:511-529` prevents indefinite RTT stalls but does not avoid formatting, locking, copying, and drop counting.

Anchors emit a typed marker on each scan (`app_anchor_radio.inc:3480-3482`) and offer one stack diagnostic cycle no more often than once per second (`app_stack_workload_diag.c:683-714`, limit at line 206). Stack collection can enumerate threads and examine stack watermarks (`app_stack_diag.c:417-435`); a full RTT buffer without a confirmed reader causes a 1 ms attachment probe on a failed record (`firmware/src/stack_diag_transport.c:97-104`). The work is bounded but is still repeated throughout deployment. Clicker diagnostic work is concentrated around actions rather than permanent idle polling.

The useful change is a qualification/capture gate that prevents expensive diagnostic submission and formatting when capture is inactive while retaining fatal/error evidence and production safety checks. Keep a qualified way to sample the exact deployed configuration: stack evidence is currently part of staging policy, so simply turning off `IMEC_STACK_DIAGNOSTICS` would invalidate that evidence flow. Compare callback counts and charge per scan/click with capture enabled and disabled, and rerun stack, timing, collision, and recovery qualification because logging can affect scheduling. Do not disable `IMEC_MESH_ROUTE_TEST`; it enables the production runtime itself.

### 3. Park unused clicker peripherals before the terminal status hold

`clicker_hold_terminal_status()` sleeps for the required 2,000 ms (`app_clicker.c:3472-3476`, `firmware/include/status.h:17`). The normal-click handler stops BLE advertising/scanning before this hold (`app_clicker.c:3501-3525`), but complete Bluetooth disable and SPI/pin parking happen during subsequent idle entry (`app_clicker.c:4086-4148`). The action worker already sleeps during the hold, so replacing its sleep is not a saving.

Evaluate moving the existing peripheral shutdown earlier once exact radio/report ownership is clear, while leaving the status LED, hold duration, action watchdog, and FIFO semantics unchanged. This could remove up to the terminal hold's residence time from unnecessary controller/peripheral readiness; actual current reduction is unmeasured, and a stopped BLE controller may already release its clocks. A failure in the earlier shutdown must keep the same bounded recovery guarantees. Test normal success, no-anchor failure, self-test success/failure, and a queued press during the full LED hold.

### 4. Evaluate anchor SPI/pin parking only during proven low-duty gaps

Clicker retained idle calls `dwm3000_port_float_pins()` (`app_clicker.c:4113-4128`). That helper explicitly suspends/disables SPIM, disconnects SCK/MISO/MOSI, and parks control pins (`dwm3000_port.c:118-138,275-308`). Anchor standby calls the DWM3000 sleep path (`app_anchor_commands.inc:288-319`, `dwm3000_driver_io.inc:195-271`) but does not use that port parking helper. This difference is proved; excess SPIM or GPIO current on the physical board is not.

Measure the gap with and without explicit port suspension. If useful, retain the existing guard lease until both radio sleep and port parking are proven, and restore the port before any subsequent access. Added resume time must fit the wake-detection bound; never float pins or suspend the bus during enumeration, survey, the click delivery listener, ACK turnaround, or a ranging reservation. A blanket call on every `idle()` would violate those ownership intervals.

## Larger gains that require a timing or hardware decision

**IRQ-assisted long receive waits.** The common driver status loop reads SPI and busy-waits 50 us until a match, timeout, or abort (`dwm3000_driver.c:262`, `dwm3000_driver_radio.inc:1057-1146`). This prevents MCU sleep during that portion of RX, including longer discovery/control waits. A radio IRQ plus bounded timeout could remove much of the active MCU polling while keeping the receiver on. The application overlay only binds reset/wakeup GPIOs for the DWM3000 (`firmware/app/app.overlay:262-270`), and the port explicitly identifies its implementation as status polling (`dwm3000_port.c:207-210`). There is no demonstrated connected IRQ in this source, so hardware pin availability and worst-case wake latency must be established first. Initially restrict such work to long control RX; delayed DS-TWR response/final deadlines, abort ownership, PHY-error signaling, and complete-frame-at-timeout behavior all need separate proof. Do not replace the 50 us wait globally with a millisecond sleep.

**Battery indication versus minimum idle charge.** Production presets explicitly enable battery indication (`CMakeLists.txt:287-290`). The indicator pulses one LED for 50 ms every 10 seconds on clickers and every 5 seconds on anchors (`app_battery_indicator.c:18-20`), a commanded LED duty of 0.5% and 1% respectively, slightly lower in wall time because ADC handling adds overhead. Every pulse also samples the divider after a 6 ms settling sleep (`app_board.c:231-245`): at least 0.06% and 0.12% divider-on settling duty, excluding conversion and scheduling time. For illustration only, if a lit LED draws 1 mA, those duties contribute approximately 5 uA and 10 uA average. The board's actual LED current was not measured.

Reducing pulse frequency/brightness, showing healthy battery only on interaction, or caching voltage between pulses can save energy, but changes visible status or sample freshness specified by `firmware/app/Kconfig:158-168`. Preserve immediate click and self-test feedback. Crucially, production clickers coalesce watchdog service into the indicator checkpoint (`app_watchdog.c:53-57,111-122`; `app_battery_indicator.c:100-102`), so removing its periodic work without replacing that service causes resets. Cached sampling must define a maximum stale interval and how threshold crossings are handled.

**Wake trains and scan cadence.** Default anchors wait 380 ms between 10 ms scans (`Kconfig:350-365`, `prj.conf:24-25`). The configured accounting adds 2.5 ms startup and 0.17 ms PLL time (`app_config.h:240-250`), giving a modeled 392.67 ms period, 2.55% RX duty, and 3.23% DWM awake duty. These are model calculations, not measured board current or measured complete-cycle duration. In 30 otherwise idle anchors, the same per-node duty applies; larger populations primarily add contention and protocol-active residence.

Ordinary click wakes remain 500 ms. An uplink to a parent outside the active click cohort uses a wake budget covering two scan periods including a 40 ms rearm allowance (`app_config.h:264-281`): at a 380 ms interval and 10 ms RX slice this is `2 * (380 + 40 + 10) = 860 ms`. Sleeping longer reduces anchor idle duty but increases contact cost and can cause whole-click retries if the click wake no longer overlaps a complete decodable frame. Shortening the 10 ms scan can miss the combined Here-I-Am packet cadence. Any adjustment therefore needs worst-phase complete-frame capture, one missed scan, mixed configured intervals, hidden relays, and loaded 30-node scenarios, followed by physical RF-distance qualification. The 40 ms allowance is a conservative configured guard; comments describing older full reconfiguration timings are not a fresh measurement of the current fast-PHY path.

**Keep the current click-parent listener optimization.** The 2026-09-05 C5 bank skips a parent wake only when the parent is a listed click participant and the shared listener is active (`app_mesh_report_c5_batch.inc:432-442`). That listener lasts `50 ms * selected_anchor_count + 200 ms`, i.e. 400 ms for four participants (`app_config.h:174,189-201`). This deliberately spends receiver energy to avoid an 860 ms parent wake. Removing the listener may increase total network charge and delivery failure. Never infer that an arbitrary cached parent is awake merely because it has a route. The current bank ACK bound is 250 ms (`app_mesh_report_c5_batch.inc:5,163`); shortening it needs measured worst-case admission, ACK construction, and turnaround under load.

## Existing power protections worth retaining

- Retained System ON is the clicker deployment default; System OFF is a profiling/recovery option (`Kconfig:18-47`, `prj-clicker.conf:11-12`). System OFF adds reset/boot latency and complicates pending button gestures, watchdog adoption, and preserved identity. It is not a drop-in lower-power replacement.
- BLE courtesy scanning is passive with a configured 32/40 scan-window ratio while active (`app_config.h:104-105`, `app_clicker.c:2985-2994`), then stops after the courtesy gate and disables Bluetooth before idle (`app_clicker.c:3149-3203`). The ratio alone does not establish actual controller duty under advertising coexistence. Removing courtesy or reducing it can cause additional full UWB retries when clickers overlap.
- DWM3000 standby retains its configuration and wake sources (`dwm3000_driver.c:250-258`, `dwm3000_driver_io.inc:241-265`). Wake uses slow SPI before readiness/restore and switches to fast SPI after (`dwm3000_driver_radio.inc:761-840`). Those ordering constraints prevent known sleep/wake failures.
- Idle pin parking and wake-arm failures are handled transactionally before a clicker claims idle (`app_clicker.c:4086-4148`). Most long application waits already use kernel sleep; `sleep_precise_us()` sleeps whole milliseconds and busy-waits only the remaining fraction (`app_state.c:814-839`).
- Full CIR collection is off by default (`Kconfig:170-178`), production RF activity LEDs are suppressed (`Kconfig:150-156`), and normal click ranging ends after FINAL rather than waiting for an extra REPORT. These are existing savings, not additional proposals.

## Validation order

1. Fix and fault-test the battery-divider cleanup contract, then prove that the next gesture and next sample work after each recoverable failure.
2. Measure battery-powered clicker idle, held-button idle, a complete click including its unchanged status hold, self-test, no-anchor retries, and interference retries. Separate MCU, UWB, BLE, and LED intervals, and compare probe-detached measurements with supervised traces; do not derive battery life from debug-attached supply current.
3. Measure anchor low-duty scans, direct report upload, hidden-parent upload, active click-parent listening, enumeration/survey residence, and route-loss/backpressure. For 30 nodes include dense siblings and relay bottlenecks, because total retries and listener duration can dominate nominal per-frame savings.
4. Before any timing/radio implementation is trusted, run focused native coverage and the mandatory `mesh_integration` and `hardware_models` gates serially, build the exact production roles, and retain current stack/RAM qualification. Power measurements cannot certify recovery or delivery; protocol success traces cannot certify low current.

No current, mAh/day, or battery-life improvement is claimed by this audit. The code proves the avoidable work and configured duty calculations above; charge savings and hardware-dependent changes remain to be measured.
